# PROJECT: PenTab Android Virtual Writing Tablet

## ROLE

Act as a senior Android developer, Flutter engineer, real-time communication engineer, UI/UX designer, and software architect.

Build a complete, functional Android application named PhonePad that turns an Android smartphone into a virtual writing tablet for teaching, presentations, online classes, and screen annotation.

The user does not own a physical pen tablet and wants to use their phone to write on their existing Windows PC without installing or developing a dedicated Windows companion application.

Do not build a UI-only prototype. Implement the actual drawing functionality and a practical connection workflow.

Before implementation, evaluate technical feasibility and choose the simplest reliable architecture that satisfies the requirements without paid infrastructure.

---

# 1. CORE REQUIREMENT

The user opens PhonePad on Android and connects it to a Windows PC.

The phone displays a landscape writing interface with:
- A central writing canvas.
- A configurable canvas aspect ratio matching the PC display.
- A left toolbar containing productivity and navigation tools.
- A right toolbar containing drawing controls.

The user draws or writes on the phone using a finger.

The strokes should appear in real time on a teaching canvas displayed in the PC's existing web browser.

The user must not need to install a separate Windows application, Windows service, desktop executable, or browser extension.

When the user presses Clear on the phone:
- Clear the phone's current canvas.
- Reset the current phone-side drawing session.
- Allow the user to start writing the next slide or topic immediately.

Do not automatically erase previous annotations from the PC unless the user explicitly selects a separate Clear PC Canvas action.

IMPORTANT: Do not falsely claim that phone drawing will automatically appear inside arbitrary existing Windows applications such as Notepad, PowerPoint, or third-party whiteboards without appropriate integration. Browser-based whiteboard functionality is the guaranteed initial target.

# 2. ARCHITECTURE: NO DEDICATED PC APPLICATION

Investigate and implement the following architecture.

## Android client

Build the primary application in Flutter.

Responsibilities:
- Capture touch input.
- Render the phone writing canvas.
- Maintain drawing tools and history.
- Pair with the PC browser.
- Transmit drawing events.
- Display connection status.
- Support reconnection.

## PC browser

Use an ordinary browser such as Chrome or Microsoft Edge.

The browser opens a dedicated web whiteboard session.

The web whiteboard is the receiver and renderer of drawing events transmitted by the Android app.

Do not require users to install any desktop software.

## Communication

Use a local network connection wherever possible.

Prefer a direct local connection that does not require an account, cloud database, paid hosting, or internet access.

Investigate WebSocket communication and an appropriate connection-discovery mechanism.

IMPORTANT ARCHITECTURAL CONSTRAINT:

A browser cannot generally accept arbitrary inbound connections from a phone merely because the devices share Wi-Fi. A connection endpoint must exist.

Evaluate the following alternatives and choose the most practical one:

1. A temporary local web server hosted by the Android device, with the PC browser connecting to it.
2. A local browser-accessible endpoint implemented by an existing runtime, if available without installing a dedicated PC application.
3. A self-contained hosted web receiver, with clear disclosure that internet access and hosting are required.

Prefer the first approach if it can be implemented reliably on Android.

If hosting a web server inside the Android application:
- Investigate Android network security and local-network restrictions.
- Support browser access to the phone's local IP address and port.
- Handle WebSocket upgrades correctly.
- Ensure the phone's operating system does not unnecessarily terminate the session.
- Handle browser-origin checks, pairing authorization, reconnection, and network changes.
- Never expose the unauthenticated drawing endpoint to arbitrary devices.
- Avoid requiring root access.

Do not assume that a phone-hosted web server will automatically work on every Wi-Fi network. Explain and handle client isolation, firewall restrictions, and network permission issues.

If direct USB communication cannot be supported without PC-side setup, do not promise universal plug-and-play USB functionality.

Provide Wi-Fi connectivity first.

### Step 2: Start a session

### Step 5: Start teaching

- The browser displays the whiteboard.
- The phone displays its writing canvas.
- Touch input generates drawing events.
- The browser renders those events in real time.

### Step 6: Move to the next slide

The user presses Clear on the phone.

The phone canvas becomes blank.

The connection remains active.

The PC's previous annotations remain intact unless explicitly cleared.

### Step 7: Disconnect

Provide a clear disconnect option.

Clean up sockets and temporary resources when the session ends.

# 9. DRAWING SYNCHRONIZATION

Design a reliable drawing-event protocol.

Possible event types:
- session_start
- stroke_start
- stroke_points
- stroke_end
- stroke_erase
- undo
- redo
- shape_add
- text_add
- phone_canvas_clear
- pc_canvas_clear
- state_sync
- session_end

Use unique identifiers for drawing operations.

Ensure that:
- Each stroke appears exactly once.
- Incomplete strokes are finalized appropriately.
- Undo and redo are consistent.
- Clear commands affect only their intended canvas.
- Reconnection does not duplicate drawing data.
- The browser can recover the latest drawing state after a temporary connection loss.

Keep phone canvas state and PC whiteboard state separate.

This separation is essential because the phone must be cleared for the next slide without automatically deleting previous PC annotations.
